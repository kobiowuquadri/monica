# MONICA

**Monitor · Observe · Navigate · Intervene · Check · Adapt**

MONICA is a mission health console for astronauts on long-duration missions, including missions to Mars. It covers:

- **Guided check-ins:** vital signs, symptoms, sleep and wellbeing.
- **Personal trends:** compared against an explicitly established baseline.
- **Transparent observations:** generated by versioned rules, with acknowledgement, recorded actions and follow-up check-ins.
- **Review summaries:** print-ready, with JSON export.
- **Radiation context:** historical **NASA Curiosity RAD** measurements and **NASA DONKI** space-weather events, kept strictly separate from personal health data.

Built for the **2026 NASA Space Apps Challenge**. This is a research prototype, not a validated diagnostic or treatment system, and it is not affiliated with or endorsed by NASA.

## What is real, and what is not

| Shown in MONICA | Origin |
|---|---|
| RAD dose rates, detectors B and E, 4–19 Sept 2017 (sols 1806–1820) | Imported from the NASA PDS archive `MSL-M-RAD-3-RDR-V1.0`, with units, QC flags and file provenance preserved |
| DONKI SEP, CME, GST and IPS events, 1–22 Sept 2017 | Imported from NASA DONKI via api.nasa.gov (flare/FLR requests currently fail upstream; shown as absent) |
| Learning content | Cited NASA references (HRP Space Radiation Element, JSC SRAG, NASA-STD-3001, the RAD SIS) |
| Vital signs, symptoms, wellbeing | Entered by the user; nothing is generated or simulated |
| Baselines and differences | Calculated by documented methods from identified readings |
| Demo profiles | Fictional, clearly labelled, and created with **no** health readings |

## Stack

- **Frontend:** HTML5, CSS3, vanilla JavaScript ES modules and Chart.js 4.4.7 (vendored). Static hosting on **Vercel**.
- **Backend:** Node.js and Express, with node-postgres using parameterised SQL only. Hosted on **Render**.
- **Database:** Neon PostgreSQL. Migrations live in `backend/migrations`.

## Quick start (local)

```bash
cd backend
cp .env.example .env            # set DATABASE_URL (Neon) and AUTH_SECRET
npm ci
npm run migrate
npm run seed:sources
npm run import:rad -- --from-sol 1806 --to-sol 1820
npm run import:donki -- --start 2017-09-01 --end 2017-09-22
npm run dev                     # API → http://localhost:8080
npm run frontend                # UI  → http://localhost:5173 (second terminal)
```

Without `DATABASE_URL` the API still starts, but it reports that database functionality is unavailable (`/api/ready` → 503). It never silently falls back to in-memory storage.

## API

Public:
- `GET /api/health`, `GET /api/ready`
- `GET /api/radiation`
- `GET /api/space-weather[?mode=recent]`
- `GET /api/sources`, `GET /api/reference`

Authentication (HttpOnly session cookie):
- `POST /api/auth/register`, `/login`, `/logout`, `/demo`
- `GET /api/me`

Owner-scoped (every `:id` is checked against the signed-in user):

```
GET  /api/profiles                           POST  /api/profiles        PATCH /api/profiles/:id
GET  /api/profiles/:id/overview
POST /api/profiles/:id/check-ins             (Idempotency-Key header required)
GET  /api/profiles/:id/check-ins[/:checkInId]
GET  /api/profiles/:id/trends?metric=&from=&to=
GET  /api/profiles/:id/baselines             POST  /api/profiles/:id/baselines
POST /api/profiles/:id/baselines/:baselineId/retire
GET  /api/profiles/:id/observations[/:obsId] POST  /api/profiles/:id/observations/:obsId/{acknowledge,close}
GET  /api/profiles/:id/actions               POST  /api/profiles/:id/actions   PATCH /api/profiles/:id/actions/:actionId
GET  /api/profiles/:id/history
GET  /api/profiles/:id/report?from=&to=
```

NASA imports are **CLI-only** (`npm run import:rad`, `npm run import:donki`); no HTTP endpoint can modify NASA data.

## Security and privacy

- Passwords: scrypt with a per-user salt.
- Sessions: opaque random token in an `HttpOnly` cookie, stored server-side as an HMAC. No credentials live in localStorage.
- Owner check on every personal endpoint. Another user's profile returns 404, so IDs cannot be probed.
- CSRF protection: a custom header plus an Origin check.
- CORS limited to the origins listed in `ALLOWED_ORIGINS`.
- Helmet security headers, plus a strict CSP on the frontend.
- Rate limits on authentication, demo creation and writes. Request bodies are capped at 64 KB.
- Error messages are generic and never expose SQL or stack traces.
- Logs record method, path, status and duration only. The audit trail stores identifiers and counts, never health values.
- Check-ins are idempotent: retries and concurrent duplicates create exactly one record.
- Demo accounts are isolated per session and deleted after 24 hours.

## Tests

```bash
cd backend
npm test                 # 30 unit + 13 integration tests
```

The integration tests run the real Express app against Neon inside a **throwaway schema** that they create, migrate and drop. They cover:
- check-in storage and retrieval;
- validation;
- cross-user denial;
- duplicate and concurrent submissions;
- unknown values staying unknown;
- no comparison without a baseline;
- follow-up completion;
- report ownership;
- demo isolation;
- RAD import deduplication and provenance;
- NASA failure handling.

Browser QA covered desktop (1440 px), tablet (820 px) and mobile (390 px):
- no horizontal overflow and no console errors;
- keyboard-only sign-in;
- mobile navigation focus management;
- a dropped connection during save shows **Not saved**, keeps the entries, and a retry creates exactly one record.
